# T1055 · C3 — Process Hollowing: One Sensor, and the Field It Lies About


## 1. Where C3 Sits

T1055 is covered as **one parent + four detection clusters**, not twelve sub-technique rules — because sub-techniques are split by *adversary method* while detections are split by *telemetry primitive*, and the two do not line up.

| Cluster | Subs | Primitive | Ceiling | Status |
|---|---|---|---|---|
| C1 Remote thread | .001, .002 | Sysmon EID 8 CreateRemoteThread | 0.85 | separate file |
| C2 Thread-less | .003, .004 | EID 8 blind — EID 10 access rights only | 0.5 | pending |
| **C3 Image replacement** | **.012, .013** | **Sysmon EID 25 + EID 1** | **0.8** | **this file** |
| C4 Linux/macOS | .008, .009, .014 | auditd ptrace / `task_for_pid` | 0.7 | out of scope |

---

## 2. Scenario and Detection Thesis

A legitimate binary is launched, its in-memory image is replaced before it runs, the entry point is repointed, and execution resumes. The process list still shows `notepad.exe` — correct path, correct on-disk hash, valid signature. The malice exists only in memory.

> **EID 25 is the only sensor that sees this, and it sees exactly one shape of it.** Sysmon ProcessTampering fires on image replacement and herpaderping. It is blind to every injection that leaves the target's image intact — DLL injection, shellcode into fresh RWX, APC, thread hijacking. C3 is not "process injection detection"; it is **image-tampering injection detection**, resting on a single sensor.

The second thesis is about a field, and it is what the rule is actually built around:

> **EID 25's `Image` cannot be trusted.** It is frequently `<unknown process>`. The reliable identity lives in EID 1, joined on `ProcessGuid`. Every downstream decision — allowlist, confidence tier — must key on the *resolved* image, never on the raw tamper field.

## 3. Lab Setup

| Component | Detail |
|---|---|
| Host | Windows 11, Sysmon **v15.20** (also a dev/VM box — see §5) |
| Tamper telemetry | Sysmon **EID 25** (ProcessTampering), `Type: Image is replaced` |
| Enrichment | Sysmon **EID 1** (process create), correlated on `ProcessGuid` |
| Generation | Atomic Red Team **T1055.012** — FuzzySecurity `Start-Hollow.ps1` (section-based) |
| Splunk | `index=windows_sysmon`, `sourcetype=XmlWinEventLog` → `index=risk` feeder |
| Sentinel | `Sysmon` parser, Scheduled Analytics rule, `TrustedProcesses` watchlist |

### Preconditions

- **Sysmon ≥ 13.** EID 25 was introduced in Sysmon 13; older builds silently ignore the `<ProcessTampering>` config line without erroring. Confirmed v15.20 via `Sysmon64.exe -c`.
- **EID 25 enabled** — SwiftOnSecurity v74 base, `onmatch="exclude"`, only Edge excluded.

### Generation failed first — and the sensor was not the reason

The first `Invoke-AtomicTest T1055.012` run failed **all four tests**: the PowerShell test threw a `ParentPID` array-transformation error, the VBA RunPE was access-denied, and both Go tests failed at `VirtualAllocEx`. No hollow occurred, so no EID 25 was produced. The instinct is to debug the detection; the correct move is to confirm the technique actually fired.

Root cause: the atomic's `$ppid = Get-Process explorer | select -expand id` returns an **array** when multiple `explorer` instances exist (normal on Win11), while `Start-Hollow` expects `[int]`. Fixed by calling the script directly:

```powershell
. "C:\AtomicRedTeam\atomics\T1055.012\src\Start-Hollow.ps1"
$ppid = Get-Process explorer | Select-Object -First 1 -ExpandProperty Id
Start-Hollow -Sponsor "C:\Windows\System32\notepad.exe" `
             -Hollow  "C:\Windows\System32\cmd.exe" `
             -ParentPID $ppid -Verbose
```

Verbose output confirmed a clean hollow: section created from file handle → `.text/.data/.rdata` duplicated into the sponsor → `ImageBaseAddress => 40000000` → PEB `pProcessParameters` rewritten → hollow main thread created → `True`. The window titled "Hollow" was running `cmd.exe` internally.

## 4. The Telemetry — and the Trap in EID 1

One hollow produced a matched pair on the same `ProcessGuid` (PID 16732):

**EID 25** — `Image: C:\Windows\System32\notepad.exe`, `Type: Image is replaced`, user context.
**EID 1** — same GUID, `Image: notepad.exe`, `ParentImage: explorer.exe`, `CommandLine: notepad.exe`, `IntegrityLevel: Medium`, `Hashes:` **the genuine notepad hash**.

**There is no mismatch in the EID 1 row.** Clean command line, real hash, correct path — because the tool launches the *actual* on-disk notepad and only rewrites memory afterwards. **EID 1 is captured at process birth, when the image is still clean.**

This kills the intended design. The original plan was an EID 1 backbone — suspended create plus path/hash mismatch — with EID 25 as corroboration. On this variant the backbone produces nothing. EID 1 survives in the rule for a different job: **identity resolution**, not detection.

## 5. Baseline — Legitimate Tampering Is Everywhere

EID 25 on an idle host is **not empty**. Six distinct benign profiles appeared across both platforms; the differing counts are an artifact of *when* each baseline ran, not of platform capability.

| Profile | Image | User | Why it tampers | Splunk (1h idle) | Sentinel (3d) | Suppressed by |
|---|---|---|---|---|---|---|
| Azure Arc | `gc_worker.exe` | SYSTEM | guest-config self-modification during compliance scans | ✔ | ✔ | path allowlist |
| Azure Arc (unresolved) | `<unknown process>` | SYSTEM | same agent, image unresolved at tamper time | ✔ | ✔ | allowlist **after** EID 1 resolution |
| MinGW toolchain | `cc1.exe`, `as.exe`, `ld.exe`, `collect2.exe` | user | GCC build subprocesses rewrite their image | — | ✔ | `has "mingw64"` |
| VirtualBox | `VBoxNetDHCP.exe`, `VirtualBoxVM.exe` | user | suplib hardening protects its own image | — | ✔ | watchlist (path) |
| Session manager | `smss.exe` | SYSTEM | session init at boot | — | ✔ | 0.40 tier, below threshold |
| Unresolved (misc) | `<unknown process>` | SYSTEM / user | target died before Sysmon resolved the image | ✔ | ✔ | 0.40 / 0.60 tier |

Three profiles are absent from the Splunk column purely because no build or VM activity ran during that one-hour window. **Legitimate injection is the central problem of T1055**, and it showed up on a host with essentially nothing installed but a management agent.

**The FP profile of a lab is not the FP profile of production.** MinGW and VirtualBox exist here because this host compiles code and runs hypervisors. A real endpoint has neither, and none of those allowlist entries transfer. Stated plainly so the numbers below are not read as a production baseline.

**Allowlist mechanics — a deliberate split.** A bounded set of named binaries (Azure Arc, VirtualBox's handful of tamper-producing executables, VS Code) goes in the watchlist as exact paths. A deep tree of 100+ executables (the MinGW toolchain) is matched by path substring in the rule instead of enumerated. Both are **path-anchored**, so neither is defeated by renaming a dropper to `gc_worker.exe`.

## 6. Scoring Model — and the Two Bugs That Made It Wrong

Framework: `risk = impact × confidence`. Impact **60** (evasion + trust inheritance). Confidence ceiling **0.80** for C3 (parent ceiling 0.85).

| Condition | Confidence | Risk | Meaning |
|---|---|---|---|
| Resolved image, not allowlisted | 0.80 | **48** | clear tamper on a known process — alerts |
| `<unknown process>`, non-SYSTEM | 0.60 | 36 | unresolved, user context — still suspicious |
| `<unknown process>` or `smss.exe`, SYSTEM | 0.40 | 24 | unresolved + system context — feeder only |

`confidence` here measures **how specific the signal is to the technique**, not a measured probability that the event is malicious. `impact × confidence` produces a prioritisation score, not a likelihood.

### The two bugs

Both came from trusting the tamper event's own `Image` field.

**1 — The allowlist keyed on EID 25's `Image`.** On the legitimate Arc events that field is `<unknown process>`, not a path, so the allowlist matched nothing and Azure Arc scored **48 — identical to the real hollow.** The rule could not distinguish a management agent from an attack.

**2 — The confidence downgrade never fired.** The condition compared against the literal `<unknown process>`, but the raw XML value is HTML-escaped `&lt;unknown process&gt;`. String equality failed silently, so every event fell through to the 0.80 default — including the ones the tiers existed to demote.

Both fixes are structural, not cosmetic:

- **Unescape `&lt;`/`&gt;` before any comparison.**
- **Resolve identity through EID 1 *before* the allowlist and the confidence tiers.** The three Arc rows that arrived as `<unknown process>` become `gc_worker.exe` once joined by `ProcessGuid` — and only then can the allowlist see them.

The enrichment join does not decorate the alert. It **re-identifies events the tamper sensor could not name**, and that identity is what every subsequent decision acts on.

## 7. The Rule

Correlation core, identical in shape on both platforms: pull EID 25 and EID 1 into one stream → collapse per `ProcessGuid` → resolve identity → allowlist → tier → score.

### Splunk (SPL)

```spl
index=windows_sysmon (EventCode=25 OR EventCode=1)
| eval Image=replace(replace(Image,"&lt;","<"),"&gt;",">")
| stats
    values(eval(if(EventCode==25, Type,  null()))) as tamper_type
    values(eval(if(EventCode==25, Image, null()))) as tamper_image
    values(eval(if(EventCode==1,  Image, null()))) as proc_image
    values(ParentImage)    as ParentImage
    values(CommandLine)    as CommandLine
    values(Hashes)         as Hashes
    values(IntegrityLevel) as IntegrityLevel
    values(User)           as User
    max(_time)             as _time
    by ProcessGuid, Computer
| where isnotnull(tamper_type)
| eval resolved_image = coalesce(proc_image, tamper_image)
| eval src_lower    = lower(resolved_image)
| eval parent_lower = lower(ParentImage)
| eval is_allowlisted = if(
      match(src_lower,    "azureconnectedmachineagent.*gc_worker\.exe$")
   OR match(parent_lower, "gc_arc_service\.exe$"), 1, 0)
| where is_allowlisted=0
| eval confidence = case(
      resolved_image=="<unknown process>" AND User=="NT AUTHORITY\\SYSTEM", 0.40,
      resolved_image=="<unknown process>", 0.60,
      1==1, 0.80)
| eval impact=60, risk_score=impact*confidence
| table _time, Computer, User, ParentImage, resolved_image, CommandLine,
        tamper_type, Hashes, IntegrityLevel, confidence, risk_score
| sort - risk_score, - _time
```

Two decisions worth naming. **`stats by ProcessGuid` instead of `join type=left`** — a left join on EID 1 is a subsearch, subject to the 50k row cap and a silent truncation failure mode; the same lesson applied in the T1200 port. And **`where isnotnull(tamper_type)` after the stats, not before** — the base search must include EID 1 to have anything to resolve with, so the tamper requirement is enforced on the collapsed row, not on the raw event.

### Sentinel (KQL)

```kql
let TrustedProcs = _GetWatchlist('TrustedProcesses') | project TrustedImage = tolower(Process);
let Tamper =
    Sysmon
    | where EventID == 25
    | project TamperTime = TimeGenerated, Computer, ProcessGuid,
              tamper_image = Image,
              TamperType = column_ifexists("Type",""),
              TamperUser = column_ifexists("User","");
let Proc =
    Sysmon
    | where EventID == 1
    | project ProcessGuid, proc_image = Image,
              ParentImage, CommandLine,
              Hashes = column_ifexists("Hashes",""),
              IntegrityLevel = column_ifexists("IntegrityLevel","");
Tamper
| join kind=leftouter (Proc) on ProcessGuid
| extend resolved_image = iff(tamper_image == "<unknown process>" or isempty(tamper_image),
                              proc_image, tamper_image)
| extend resolved_image = iff(isempty(resolved_image), "<unknown process>", resolved_image)
| extend ri_lower = tolower(resolved_image)
| extend is_mingw       = ri_lower has "winlibs" and ri_lower has "mingw64"
| extend is_watchlisted = ri_lower in (TrustedProcs)
| where iff(is_watchlisted or is_mingw, 1, 0) == 0
| extend is_unknown = iff(resolved_image == "<unknown process>", 1, 0)
| extend is_system  = iff(TamperUser has "SYSTEM", 1, 0)
| extend is_smss    = iff(ri_lower endswith "smss.exe", 1, 0)
| extend confidence = case(is_smss == 1 and is_system == 1, 0.40,
                           is_unknown == 1 and is_system == 1, 0.40,
                           is_unknown == 1, 0.60,
                           0.80)
| extend impact = 60, risk_score = impact * confidence
| where risk_score >= 30
| extend Severity = case(risk_score >= 48, "High", risk_score >= 36, "Medium", "Low")
| project TamperTime, resolved_image, TamperType, TamperUser, ParentImage, CommandLine,
          Hashes, IntegrityLevel, is_unknown, confidence, risk_score, Severity, ProcessGuid
| order by risk_score desc, TamperTime desc
```

The allowlist is implemented platform-natively — regex on a full path in SPL, watchlist lookup plus path substring in KQL — but the *anchor* is the same in both: the resolved path, never the process name.

### Known parity gaps

The two rules are not yet byte-equivalent. Documented rather than quietly patched, because the validation figures in §8 were produced by these exact queries:

| # | Gap | Effect | Fix |
|---|---|---|---|
| 1 | **Resolution precedence is inverted.** SPL prefers EID 1 (`coalesce(proc_image, …)`); KQL prefers the tamper image and only falls back to EID 1 | Identical output today, since EID 25 is only wrong when it is `<unknown>`. Diverges the moment EID 25 reports a *stale but non-empty* image | Align both on EID-1-first |
| 2 | **SPL has no threshold and no `collect`.** KQL filters `risk_score >= 30`; SPL emits every row including the 24s and never writes to `index=risk` | SPL is a search, not yet a feeder — 0.40-tier rows would flood the risk index | Add `| where risk_score >= 30 \| collect index=risk` with the scan window equal to the cron interval |
| 3 | **`tamper_type` is never filtered.** Both rules accept any ProcessTampering type, not just `Image is replaced` | Herpaderping and other tamper shapes score identically to hollowing | Either constrain to `Image is replaced` or split `tamper_type` into the detect_type field |
| 4 | **KQL has an `smss.exe` tier; SPL does not.** Sentinel demotes `smss.exe` via confidence, Splunk would score it 0.80 | Boot-time FP on Splunk once a fleet is onboarded | Port the tier, and reconsider — demoting a specific binary through the confidence field is really an allowlist wearing a disguise |

Gap 4 is the one that matters conceptually. Confidence tiers should describe *signal quality*; a named-binary exception is an allowlist entry and belongs in the watchlist, where it is visible and auditable.

## 8. Validation

Both the true-positive and the false-positive side were exercised, on both platforms.

| Test | resolved_image | User | Splunk | Sentinel | Verdict |
|---|---|---|---|---|---|
| Hollow #1 (notepad ← cmd) | `notepad.exe` | user | **48** | — | injection — alerts |
| Hollow #2 (notepad ← cmd) | `notepad.exe` | user | **48** | — | injection — alerts |
| Hollow #3, fresh generation | `C:\Windows\System32\notepad.exe` | user | — | **48 / High** | injection — alerts |
| Azure Arc (resolved) | `gc_worker.exe` | SYSTEM | silent | silent | allowlisted |
| Azure Arc (`<unknown>` ×3) | → `gc_worker.exe` via EID 1 | SYSTEM | silent | silent | **allowlisted only after resolution** |
| MinGW / VirtualBox / smss / `<unknown>` | various | user / SYSTEM | not in window | silent | suppressed |

**Totals:** Splunk — 5 raw EID 25 events → 2 alerts. Sentinel — 126 benign EID 25 events → **0 alerts**, plus one generated hollow at 48/High. Identical score on both platforms from independently written queries.

The Arc row is the one that proves the design. Those three events arrived with no usable identity; without the EID 1 join they either alert at 48 alongside the real attack, or get dropped as noise. Resolution is what makes the allowlist possible at all.

## 9. What This Cannot Catch

EID 25 fires on **image replacement only**. Every injection that leaves the target's on-disk image intact is invisible here — and that is most of T1055:

| Evades C3 | Why | Covered by |
|---|---|---|
| DLL injection (`CreateRemoteThread` + `LoadLibrary`) | image unchanged; a DLL is *loaded*, not replaced | C1 (EID 8) |
| Shellcode into fresh RWX | writes to a new allocation, not the image | C1 (EID 8) |
| APC injection (`QueueUserAPC`) | no thread, no image change | C2 (EID 10 only) |
| Thread hijacking (`SetThreadContext`) | no thread, no image change | C2 (EID 10 only) |
| Doppelganging / Ghosting / Transacted Hollow | some variants avoid the unmap pattern Sysmon keys on | uncertain — variant-dependent |

**And EID 1 offers no fallback.** The hollow's EID 1 row was clean (§4), so the "suspended create + mismatch" logic finds nothing on this variant. C3 caught this attack on a single sensor; had EID 25 been blind — as it is for the entire first column above — there would have been no detection at all.

This is not a strength to advertise. It is the reason C1 and C2 exist, and the reason the parent's practical ceiling on Sysmon-only telemetry is ~0.6.

## 11. Limitations & Production Readiness

**Validated.** EID 25 image-replacement detection on real hollow telemetry (Splunk 48, Sentinel 48/High). Legitimate-tamper suppression via EID 1 re-identification of `<unknown process>`. Path-anchored allowlist resistant to rename. `stats`-based correlation avoiding subsearch caps. 126 benign events → zero false positives on Sentinel.

**Not production-ready:**

- **Single sensor, single variant.** Only FuzzySecurity's section-based hollow was tested. Other hollowing and doppelganging implementations may not trigger EID 25 at all — untested. A second generation method is the next step.
- **Confidence tiers only partially proven.** The 0.80 tier fired on the real hollow and the 0.40 tier was exercised as a sub-threshold feeder, but the **0.60 user-context `<unknown>` tier still has no confirmed malicious example** — every user-context `<unknown>` observed resolved to a benign compiler subprocess, not a fast-dying malicious target.
- **The EID 1 backbone never fired.** The intended mismatch logic found no mismatch; C3 currently rests entirely on one sensor.
- **Four open parity gaps** between the SPL and KQL versions (§7), including SPL not yet being a `collect`-based feeder.
- **Lab-specific FP profile.** The baseline is dominated by dev-box noise — compiler toolchain, hypervisor — that a production endpoint would not have. The allowlist does not transfer.
- **Single host, manual trigger, user context only.** Fleet baselines will differ; `<unknown>` + SYSTEM volume needs measuring on real endpoints.

**Next:** a second hollowing implementation to test EID 25's generality; close the four parity gaps; then **C2** — APC injection, to confirm EID 8's blindness first-hand and build the EID 10 GrantedAccess correlation chain.
