# T1059 — Command and Scripting Interpreter: Two-Layer Detection via Process Lineage and Script Content


# 1. Scenario

A Meterpreter `reverse_tcp` payload is delivered via a `certutil` download cradle, executed, and used to spawn an interactive command shell. The operator runs a host-discovery burst inside that shell.

But the detection thesis is not about this one payload. T1059 is the hardest false-positive problem in the matrix: `powershell.exe ran` and `cmd.exe ran` carry **zero information** — the interpreter running is normal. Every admin, every EDR agent, every login script, every SCCM package spawns them. What is scored is not that the interpreter ran, but **how** it ran: the parent that spawned it, the arguments it carried, and — where telemetry allows — the content it executed.

That last clause forces a two-layer design. Process-create telemetry (Sysmon EID 1 / Endpoint DM) sees lineage and command line but **cannot see decoded script content** — an encoded PowerShell command appears only as a base64 blob. Per ATT&CK v19, this caps process-create confidence at 0.7. Seeing the deobfuscated payload requires **EID 4104 ScriptBlock Logging**, which lifts the ceiling to 0.9. The same encoded command is therefore scored by two independent feeders — one reading lineage, one reading content — and correlated in the risk layer.

This writeup builds both feeders, migrates the process-create layer to accelerated `tstats`, and hardens two production gaps: parent-name **masquerading** and **indicator-removal blindness**.

# 4. The Scoring Model

Portfolio-wide framework: `risk = impact × confidence`, held constant across techniques. Per ATT&CK v19 for T1059:

**Impact** — the interpreter alone is directionless (impact lives in what it carries), so the base is low and raised by context:

| Context | Impact |
|---|---|
| Standard execution | 50 |
| SYSTEM / High integrity | 65 |
| Remote WMI / WinRM (lateral) | 70 |

**Confidence** — calibrated to ATT&CK's v19 reference points:

| Reference | Calculation | Meaning |
|---|---|---|
| `50 × 0.0` | bare `powershell.exe ran` | Zero information — not even a feeder |
| `65 × 0.85` | anomalous parent (Office/web → interpreter) | Direct-alert territory |
| `65 × 0.60` | encoded command, decoded via 4104 | Download-cradle content |
| Process-create ceiling | **0.85** | Lineage + arguments, no content |
| 4104 ceiling | **0.90** | Decoded script content visible |

The two ceilings are the architecture. Process-create can never see content, so it caps below 4104 — exactly the v19 statement that "with 4104 disabled, confidence locks at 0.7." Enabling 4104 is the **detectability precondition** for this technique, not an optional enhancement.

# 5. Layer 1 — Process-Create Feeder (`tstats` / Endpoint DM)

## 5.1 Why tstats

The initial rule read raw `index=windows_sysmon` over a 30-day window. Migrating to the accelerated Endpoint data model cuts that to a summary read. The critical precondition: **does `Processes.process` retain the full command line?** Verified before migrating —

```
Processes.process: "C:\WINDOWS\SystemTemp\...\chrome_installer.exe" --verbose-logging --do-not-launch-chrome --channel=stable
```

Arguments intact. So `enc`, `cradle`, `bare_cmd`, `stealth` all survive the move. Had `Processes.process` held only the exe name, `tstats` would have destroyed the rule's entire value (command-line analysis) — the migration would have been a downgrade, not an upgrade.

One semantic shift matters: raw `ParentImage` held only the parent's exe path; CIM `parent_process` holds the parent's **full command line**. This *added* real signal — `mshta.exe "...\Downloads\bill.hta"` now scores `susp_path` on the HTA argument, which raw telemetry missed — but also introduced a false `susp_path` on `w3wp.exe` (its config path contains `\temp\`). The latter is dominated by `parent_lineage=4` and does not affect the verdict. Data-model migration changing signal semantics is a subtlety most miss.

## 5.3 Signals

| Signal | Weight | Meaning |
|---|---|---|
| `parent_lineage` | 4 | Interpreter spawned by Office / web server / SQL — the strongest single indicator, direct-alert per v19 |
| `untrusted_parent` | 3 | Parent runs from a user-writable path (`Temp`, `temp_test`, `AppData\Local\Temp`) outside `Program Files` |
| `susp_path` | 1 | Suspicious token in parent path/args |
| `bare_cmd` | 1 | `cmd.exe` with no arguments → interactive shell channel |
| `enc` | 2 | Base64 `-enc` / `-EncodedCommand` |
| `stealth` | 1 | `-w hidden` window suppression |
| `chain` | 1 | `cmd /c powershell` lineage |
| `cradle` | 2 | Download-cradle tokens (`Net.WebClient`, `certutil -urlcache`, `bitsadmin`) |
| `exec_bypass` | 1 | `-ExecutionPolicy Bypass` — **only when combined** with another signal (see §5.4) |

## 5.4 False-Positive Analysis

Real benign traffic surfaced over the 30-day window, tuned out behaviourally rather than by path exclusion:

| Class | Signal that fired | Resolution |
|---|---|---|
| VS Code / Claude Code driving `cmd` | `susp_path` (AppData) | Removed `AppData`/`Users` from `susp_path`; allowlisted by name+path |
| Realtek driver `-ExecutionPolicy Bypass` | `exec_bypass` | `exec_bypass` gated — fires only alongside `susp_path`/`cradle`/`enc` |
| Signal / Discord / Spotify auto-updaters | `untrusted_parent` (AppData) | Name+path allowlist (§7) |
| App prereq checks (`exit 0/1`, `Get-Command`) | `untrusted_parent` | `benign_check` — behavioural filter on command content |
| Own triage (`Get-WinEvent ... DownloadString`) | `cradle` | `is_logquery` gate — log-read is not a download |

Two design points are load-bearing. **`exec_bypass` alone is not a signal** — legitimate installers (Realtek, VS Code) use it constantly; only `Bypass` *combined* with a suspicious path or download scores. **`benign_check` is behavioural, not path-based** — app updaters run prereq checks (`exit 0/1`, `.StartsWith(`, `Get-ExecutionPolicy`); the same filter catches Signal, Discord, and any future updater with one rule, rather than a per-app exclusion list.

## 5.5 Validated Output

| Event | Signals | risk_score |
|---|---|---|
| `w3wp → cmd /c certutil` | lineage4 + cradle2 + susp1 | **52.65** |
| `w3wp → cmd` discovery ×10 | lineage4 + susp1 | 48.75 |
| **`update.exe → cmd`** (Meterpreter) | untrusted3 + susp1 + bare1 | **42.25** |
| `mshta → powershell` | lineage4 + stealth + bypass | 40.50 |
| enc-only tests | enc2 | 13.00 (feeder only) |

`update.exe → cmd` sorts above every benign event — the Meterpreter shell, on a masqueraded binary, correctly outranks noise. In the first iteration (before `parent_lineage` and `untrusted_parent`) this same event scored 15.60, *below* a benign VS Code install. The signals that fixed it are the two the original rule lacked.
